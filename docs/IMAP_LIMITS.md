# IMAP 响应限额与分段成本

状态：2026-11-11，A3.8。实现位于 `src-tauri/src/imap_limits.rs`，分段算法位于 `mail_recovery_segments.rs`。真实服务器吞吐与服务端兼容性仍待授权测试账号验收。

## 读取边界

账号验证和生产同步都在 IMAP 库之前包裹 LimitedStream。同步的层次为 TLS → LimitedStream → TracedStream（COPYUID）→ imap 库缓冲 / 解析；SMTP 沿用自己的限制。不能只在 FETCH 返回之后检查大小，因为库已经接收并缓冲了响应。

| 限额 | 当前值 | 计数范围 |
| --- | --- | --- |
| 单个 literal 声明 | 16 MiB | FETCH、LIST 等数据响应的原文字节 |
| 响应总字节 | 32 MiB | 一条已 flush 命令的所有响应，包含正文、协议文本和 unsolicited 数据 |
| 单行协议文本 | 1 MiB | 不含 literal 内的行；无换行输入也逐块受限 |
| 协议行数 | 10000 | 同一命令响应，literal 内容不计作协议行 |
| SEARCH UID token 数 | 50000 | 同一命令的多行合计，重复 token 也计数 |
| 上游单次读取 | 8192 字节 | 即使库请求更大的 buffer，也不做巨量 socket read |

literal 十进制长度使用 checked arithmetic；超限或整数溢出时，拒绝把完整声明交给库，不继续读取其正文。解析可跨 socket 分片，跳过已声明 literal 的原文字节，正文中的 SEARCH / COPYUID / 超长文本行不当作协议。普通 OK 说明文字中的 `{数字}` 不用来跳过后续协议。

任何流式拒绝使整个连接永久失效，Read / Write / flush 都不再访问底层连接。不能截断 SEARCH / BODY 后返回成功、排空继续、重新补预算后复用连接或依据此前出现的 COPYUID 确认 MOVE。错误映射不包含原始协议、密码或邮件正文。

预算只在 imap 2.x 的 a<数字> 空格标签命令成功 flush 时重置；有限状态机不保存命令内容。空 flush、IDLE DONE、AUTHENTICATE 的 base64 / 空 continuation 不重置预算。没有 APPEND / 命令流水线；未来增加须重新定义总预算并补测试。

单命令总时间 60 秒，worker 从开始执行计 300 秒；socket 10 秒，读写边界检查取消。部分协议行 / literal 中超时使连接永久失效，不能由 IDLE 丢弃半行后复用。STARTTLS 30 秒、64 KiB 总响应 / 8 KiB 行、只读到升级成功边界，不发送凭据或降级明文。系统 DNS / TLS 调用仍可能延迟停止。

库在限额内组装响应，MIME 有额外内存；传输字节上限不等于进程 RSS。

## 本地数据与绑定校验

恢复仍先精确查询 RFC822.SIZE，保留单封声明大小 1 MiB、每页合计 10 MiB 的更严格业务上限；还要验证实际正文长度、UID、完整原文指纹及可信来源。服务器虚报大小不能通过绑定验证，传输层另外限制其实际输入。不能跳过超限候选来断言其余候选唯一。

流式拒绝按 network 失败处理，保留上个完整提交的检查点、意图和缓存。当前不完整页不提交；用户明确继续后重新读取该页。普通同步不推进失败批次游标、不提前做 UIDVALIDITY 清理；先前完整批次保持。已经发出的 MOVE 遇到拒绝为 unknown，不自动重试，即使此前出现有效 COPYUID。

生产下载先读 SIZE，最多 100 UID，按声明总量 8 MiB 规划完整 BODY.PEEK 分组。大于 8 MiB 原文按 256 KiB 精确偏移分块临时落盘，核对唯一 UID / BODY 索引 / 实际长度，最后验证完整长度和 UIDVALIDITY；不接受截断为成功。最大完整原文 64 MiB，超过明确失败，不跳过邮件或推进游标。64 MiB 可跨多个 literal，但每个响应仍受上述限额。

mail-cache 配额 512 MiB，临时下载按声明长度预留、完整原文按 SHA-256 命名；配额不足只淘汰最旧完整缓存，不删除邮件 / 意图。半文件崩溃后清理，完整后落盘再关联数据库；提交失败可能留下可淘汰完整孤儿。读缓存重新核对摘要，禁止路径来自邮件附件名。

收到的附件最多投影 200 个 MIME 附件元数据，显式系统另存为；名称去路径 / 控制字符 / Windows 设备名，临时写入后原子保存。没有自动执行 / 打开 / 预览；缓存被清理可明确重新下载完整原文，此操作保留本地状态、不升级弱历史指纹。原文最终 MIME 解析与附件解码仍有额外内存，未实现任意大附件独立流式解码。

## 固定区间的密度估算

无 Message-ID 提示的 ALL 搜索，在有有效 UIDNEXT 且 EXISTS 超过 1024 时即可使用分段，不必等到旧 50000 快照上限。任意搜索的 UIDNEXT 超过 50001 时仍使用分段。无有效 UIDNEXT 时不伪造区间完整性，沿用有界小快照规则。

新建 ALL 搜索分段时，以参与文件夹的 UIDNEXT 和 EXISTS 估计区间宽度：

`span = clamp(ceil((UIDNEXT - 1) × 1024 / max(EXISTS, 1)), 1024, 50000)`

密集邮箱通常使用 1024 数值 UID 的区间；大量空洞的邮箱最多使用 50000，减少空段任务。有 Message-ID 提示的 HEADER 搜索保持 50000 宽区间，因为整箱 EXISTS 不能估计过滤后的候选密度，不能仅因整箱密集就产生大量空段。EXISTS 仅用于性能估算，不是完整性证明。每个文件夹的 span 在检查点固定；后续 EXISTS 改变不会改边界。UIDVALIDITY / UIDNEXT 的核对仍与原实现相同。

每页仍最多读 8 个原文，页前、页后均查询并比较当前段完整排序 UID 集合；collecting 完成后逐段 validating 全集并比较滚动摘要，最后复读匹配原文。确认重新完整执行两个阶段。区间不能因未匹配、为空或只有一个匹配而跳过。

在完全密集的原 50000-UID 段中，6250 页每页两次传输 50000 个 UID。改成 1024 区间后，每个满段 128 页、每页两次传输最多 1024 个 UID；主要降低反复传输、排序和检查点写入的集合规模，原文请求次数不减少。弱网络、高延迟、持续新信和稀疏 UID 仍可能很慢；此推导不能代替真实大邮箱基准。

segmented-v1 的 fence 可带 span；省略时按旧版 50000 读取，默认值序列化仍省略，保持已有摘要兼容。旧检查点继续原区间，不在中途改范围；重新开始才使用新估算。格式探测跳过未知字段，避免额外构建一棵完整 JSON Value 树；当前 UID 列表不再为页处理克隆一份。分页与分段的检查点序列化均在取得 DB Mutex 之前完成，提交仍核对 generation / revision。

## 验证入口

- `imap_limits_tests.rs`：分片 / 溢出 / 超量 literal、无换行长行、跨行 SEARCH 计数、完整 50000 UID、正文伪协议、LIST literal、总响应 / 行数、预算重置与永久失效。
- `mail_recovery_extended_tests.rs`：密集 50001 / 4096 EXISTS 使用 1024 区间、HEADER 提示保持宽区间、连续页及 EXISTS 改变时边界不变、检查点小于 10 KB、页集合改变 / 坏 span 拒绝、流式失败保留上页 / 本机修改并明确续查。既有跨段重复、全段复核和确认重扫继续覆盖。
- `mail_sync.rs`、`imap_writeback.rs`：超限不清理旧 UIDVALIDITY 缓存或推进游标；COPYUID 后超限仍 unknown、不重复 MOVE。网络脚本中检查 DB 未被持有。

测试使用本机生成的协议数据与临时数据库，没有真实邮件账号；密集用例实际检查两页原文，未遍历真实五万封邮件、测量服务器吞吐或证明固定 RSS 上限。
