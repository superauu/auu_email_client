# 旧缓存与归档结果恢复

状态：2026-11-11，A3.4–A3.6 已实现主动恢复、跨代 / 分页核对、可信旧缓存指纹补齐及大范围分段核对；使用逐命令脚本 IMAP 和浏览器 IPC harness 验证，真实服务器仍待验收。先阅读 MESSAGE_CHANGES 与 SYNCHRONIZATION。

## 操作流程

1. 旧 IMAP 缓存缺少定位代次、定位冲突或 unknown 归档，在阅读区显示“核对远端定位”。不会清库、重新建账号或自动丢弃本地修改。
2. 点击后先持久保存核对请求，再进入现有账号同步队列。核对自身只执行 EXAMINE、UID SEARCH、UID FETCH / BODY.PEEK，不执行 STORE、MOVE 或 EXPUNGE。同一账号任务中的其他邮件仍按正常同步规则处理。
3. 找到候选后显示文件夹、UIDVALIDITY、UID 和证据说明，尚未改变定位或确认归档。“确认恢复定位”会再次联网核对，只有结果与第一次证据一致才提交恢复。
4. 恢复后保留本机修改，重新排队待回写字段；下一次手动同步才写入远端。核对和确认本身不发送 MOVE。
5. unknown 归档若原邮件仍在源、目标搜索完整且无匹配，提供“重新排队归档”。这是明确的新移动请求；第二次核对仍相符才排队，之后另一次手动同步尝试移动。
6. 候选较多时展示进度，点击“继续核对下一页”；完整检查前不提供确认入口，即使已发现一个匹配。网络失败可续查已提交的页面；候选改变、重复、两边均有 / 均无或证据不足时保留原缓存。“仅保留本机”停止恢复并保留本地覆盖，不能撤销服务器操作。

登记请求成功但任务提交失败时可点击“开始已登记核对”，不重复创建请求。若请求在现有账号任务经过核对阶段后登记，durable completion 会检测 queued 请求并追加后续轮次；提交失败仍可手动重新启动。

## 证据与边界

### 旧缓存

remote_id 只提供候选 kind / UIDVALIDITY / UID，绝不单独作为验证结论。原文件夹须有已保存定位，或数据库中该 kind 唯一的文件夹映射，且在当前 LIST 的可选择文件夹中。多个候选或映射缺失时停止，不猜文件夹。

先 EXAMINE 取得当前 UIDVALIDITY。仍为原代次时，精确获取原 UID 内容；有完整原文 SHA-256 则匹配指纹，没有则要求非空正文与发件地址、主题、收件列表、正文和 INTERNALDATE UTC 时间全部一致。空正文 / 仅 HTML 或附件的旧缓存，或内部日期缺失不能比较时，不自动绑定。代次改变时走下述跨代完整候选扫描，绝不直接信任数值相同的新 UID。

无原文指纹时，不能证明未缓存的附件或其他头部一致。界面明确显示“旧缓存无完整原文指纹”，要求用户核对并确认；这种较弱证据只用于原 UIDVALIDITY / UID，不能跨代绑定。不是按主题 / Message-ID 自动去重。

### 旧缓存完整原文指纹的安全补齐

完整原文指纹是对服务器完整 BODY.PEEK 原始字节做 SHA-256，不对 bodyText、主题 / 地址组合、拼接头部或模拟原文做摘要。历史原文已经丢失且原定位也不可验证时，无法从相似的新邮件“补回”历史指纹；保留本机内容与未解决状态。

只有本机 locator_verified 为真、账号 generation 未变、remote_id 与保存的文件夹 / UIDVALIDITY / UID 元组一致时，才开放“核对并补齐原文指纹”。两次只读打开原文件夹，要求原 UIDVALIDITY 不变；两次精确读取同 UID 的完整原文，大小合法、缓存字段一致、原文摘要一致。此时只保存待确认证据，不写消息指纹。

“确认补齐完整原文指纹”再次重复上述读取并比较前一证据。事务最后再核对账号 / 消息版本，才写 content_hash 与 content_hash_verified。此操作不改邮件定位、正文、已读 / 星标 / 归档意图或其 revision，不自动发送或重新排队。途中编辑、换账号、UID 消失 / 代次改变、原文不一致、读写失败均保留原数据；空正文等无法通过现有缓存字段比较的旧缓存仍不强行补齐。

v8 增加 locator_verified / content_hash_verified 来源标记与 message_recovery.operation。已有 v7 消息只有原代次定位仍明确、账号代次一致且没有任何恢复历史记录时，才回填可信标记；有恢复历史的旧观察值保守处理，不将旧 cached-fields 确认或无法审计的摘要升级为可信历史。后续真正完整同步 FETCH 或通过上述原定位核对可以建立新的可信原文证据。普通弱内容恢复不会自行设置可信摘要，已有跨代确认检查点也不能绕过新的来源校验。

界面在无法补齐时展示原因并禁用补齐按钮；指纹补齐确认与定位恢复确认是不同操作，不能相互套用。

### 跨 UIDVALIDITY 重绑定

只在原文件夹映射仍明确、账号 generation 有效且缓存已有完整原文 SHA-256 时启用。把新一代 UID 作为全新候选，按候选搜索快照逐页获取原文匹配。旧 UID 的数值、主题、发件人或 Message-ID 都不能单独确认身份；没有完整指纹的旧缓存继续 unresolved，并保留本地修改。

只有完整集合唯一指纹匹配才展示新 UID / UIDVALIDITY，并明确说明跨代。确认时重新创建快照、重新扫完所有页面、复核候选原文及集合摘要，再比较第一次证据。确认阶段也可能分页，继续按钮保留原来的确认决定，不把它变成一次普通检查；未扫完仍不应用绑定。

本机 message ID、正文与本地状态保持；仅在最终事务更新远端定位、非 local 意图的 generation / 文件夹 / UIDVALIDITY / UID。普通同步不会据 UIDVALIDITY 改变自动把旧修改套到新 UID。若服务器保存了多个原文完全相同的副本，也视为歧义，不选第一个。

### unknown 归档

只核对意图中保存的源和目标；缺少目标或账号连接代次已变化时停止。源 UIDVALIDITY 改变但有完整指纹时，对源的新一代和保存的目标一起完整扫描；无指纹则停止。不会猜新的 Archive 或把旧移动套用到重建的账号。

读取源 UID；在保存的目标中搜索候选。有已缓存 Message-ID 时仅用 HEADER Message-ID 缩小范围，再获取内容逐个验证，Message-ID 不是身份证据；没有则搜索 ALL。新同步的邮件保存原文 SHA-256；旧 unknown 缓存可以使用上述缓存字段比较，但必须由用户明确确认其较弱证据。

扫描目标后再打开源文件夹，确认源存在性和指纹未在扫描期间变化：

| 核对结果 | 处理 |
| --- | --- |
| 源不存在、目标唯一内容匹配 | 提供确认恢复；确认时重新检查，提交后清除该 unknown 归档意图 |
| 源仍匹配、目标完整搜索无匹配 | 允许明确重新排队归档，确认时再次检查；不立即移动 |
| 源与目标都存在、多个匹配、两边都缺失 | unresolved；不选第一个、不重复移动 |
| 原代次 UID 内容不同 | unresolved；不将旧意图指向不同邮件 |
| 源 UIDVALIDITY 变化 | 完整原文指纹 + 源 / 目标完整分页核对；否则 unresolved |

两步检查不能提供跨 IMAP 文件夹的事务性快照，也不能证明其他客户端从未移动 / 删除过副本。后续远端变化仍由回写的定位 / UID 检查拒绝；不承诺 CONDSTORE、完整外部移动追踪或服务器事务锁。

## 持久化与 IPC

v6 追加 `006_remote_recovery.sql`，不改写 v1–v5：

- messages.content_hash：完整 FETCH 原文 SHA-256；messages.header_message_id：候选搜索提示。旧行保持 NULL，不用已解码正文冒充完整原文指纹。
- message_recovery：每账号 / 邮件一条请求，保存 generation、revision、action、state、detail、proof_json 和时间。证据保存定位、原文摘要与结果，不额外保存原文、密码或协议日志。
- MailMessage.recovery：可公开状态、说明、候选定位及 evidence（raw-sha256 / cached-fields）；指纹及搜索头部不经该投影返回前端。

v7 追加 recovery_scan：候选集合 / UIDVALIDITY、已检查位置、匹配摘要与跨代标识。进度单独保存，投影无需读取整个检查点。旧 v6 证据缺少新字段时按默认值读取；不把旧证据伪装为已完成跨代扫描。

`mail_request_recovery(accountId,messageId,revision,action)` 返回保存后的 MailMessage。action 为 check / confirm / retry-archive / continue / fingerprint / confirm-fingerprint。continue 保留原决定；operation 标识 recovery 或 fingerprint，服务端禁止用错误类型确认。仍只登记本机请求，联网复用账号队列。recovery 还返回 fingerprint 的 eligibility / 原因；progress 有 checked / total / matches，分段模式附带 segments `{completed,total,phase}`，phase 为 collecting / validating。

| state | 含义 |
| --- | --- |
| available | 可主动核对，尚未登记 |
| queued / checking | 已持久登记 / 正在只读核对 |
| located | 已找到候选，等待确认；此时尚未重新绑定 |
| scanning | 已提交部分页面，尚未证明唯一；继续下一页或重新核对 |
| source-present | 源仍存在、目标无匹配，允许明确重新排队 |
| stale | 候选结果后本机版本或账号代次改变；需重新核对 |
| unresolved / failed | 有歧义或不满足条件 / 网络中断；保留缓存，可重新核对 |
| restored | 已通过再次核对并提交本地恢复；不表示已完成后续回写 |
| local | 已选择仅保留本机；可主动再次检查，local 字段仍不自动上传 |

请求核对账号与邮件所有权、state_revision 及当前可确认状态。核对期间全消息版本发生变化即丢弃证据；同字段新修改、账号重配 / 删除重建均不能被旧结果清除。前端按邮件串行保存，提交最新 revision；较晚返回的低版本 IPC 不覆盖新工作区。

恢复请求与待确认结果保护原缓存：暂停该邮件意图回写，BODY 更新、FLAGS 观察和 UIDVALIDITY 清理不覆盖 / 删除它。确认恢复后释放保护；local 保留原缓存覆盖。核对状态改变递增消息版本，不能绕开版本保护直接更新状态表。

启动时 checking 转 queued，清除证据和检查点、action 退回 check，由 durable request 恢复或手动同步重新开始；不会应用中断中的旧确认。已经完整提交的 scanning 页面可跨重启保留，用户明确继续；网络失败保留上一提交检查点。仅本机、重新开始或非网络失效清除检查点。任何编辑 / 账号变化使页面过期，不能用 continue 绕过 revision / generation。

## 本地事务与副本合并

提交前再次核对账号 generation、请求 revision 和邮件版本。恢复保留原本机 message ID，更新远端定位 / 指纹与文件夹，并重新定位 queued / failed / conflict 意图；local 字段继续只在本机。unknown 归档仅在确认目标或明确重新排队时改变。

如果目标 UID 已由普通同步下载成另一缓存，只合并内容相符且没有状态意图或恢复记录的副本。标签取并集，事件与回复草稿引用转到原本机 ID；草稿 revision 递增，使在途旧保存正常冲突。删除副本、引用更新、定位和意图变更同事务，失败全部回滚。目标副本有本机编辑或内容不同，保留两份，报告 unresolved；没有自动选择哪份修改覆盖哪份的规则。

所有网络和 MIME 解析都在 DB 锁外；同账号复用已有 worker，保持全局最多两个账号并行。每个任务最多处理 20 条已登记请求，剩余继续保留 queued，由持久调度继续，仍不越过 located 明确确认。

## 有界扫描与验证

单页最多检查 8 个候选，保留单封 1 MiB 与单页声明正文总量 10 MiB（含源与最终候选复核）的限制；这样即使每封接近上限也能推进页面。超过单封上限、缺少大小、实际大小不符或候选消失，仍不跳过该候选来断言唯一。原代次、少量候选可沿用一次完成路径。

小范围恢复继续使用 v7 候选列表检查点：每页开始 / 提交前复核完整集合及源存在性，最后一页重新读取匹配原文；确认阶段重复完整扫描并比较集合摘要。匹配计数为 1 也不能提前开放确认；发现第二个匹配可以提前拒绝。

### 超过 50000 候选的分段模式

当只读打开源 / 目标取得的 UIDNEXT 超过 50001，或无 Message-ID 提示且有有效 UIDNEXT、EXISTS 超过 1024 时，改用 segmented-v1 检查点。按完整正 UID 空间分成每段最多 50000 个数值的闭区间，对每段请求 `UID SEARCH UID start:end <条件>`；A3.7 根据 UIDNEXT / EXISTS 的密度估算把新的 ALL 密集段缩小至 1024，有 Message-ID 提示的搜索保持宽区间，避免大量空段。宽度持久化后不随 EXISTS 改变，旧检查点继续按原宽度。每次只缓冲当前段 UID 列表，单页仍最多读 8 个候选原文。不存在全恢复 50000 候选的总上限；越界或超段容量响应直接拒绝，不截断响应后判断唯一。性能公式、兼容规则与验证见 [IMAP_LIMITS](IMAP_LIMITS.md)。

初始固定每个参与文件夹的 UIDVALIDITY / UIDNEXT，所有页和最终复核都要求边界不变；缺少 UIDNEXT 时不能建立大范围完整性证明。HEADER Message-ID 仍仅用于缩小候选，不作为身份证据。空区间也计入证据，不能跳过未知区域。未知归档只核对原保存的源与目标，不扩大目录权限或猜新目标。

分两阶段：collecting 逐段核对所有候选原文并维护跨段匹配数；每段结束把区间标识和完整排序 UID 集合折入滚动摘要，不保留全局大 UID 列表。全部候选检查完后进入 validating，重新查询每一个区间，重算全段集合摘要。摘要完全相同、所有边界 / 原源存在性仍一致且最终匹配原文再次核对成功，才产生可确认结果。任何一段出现第二个匹配，或全段复核发现早期区间新增 / 删除候选，都不绑定。

确认时再次从第一段开始重复 collecting + validating，再比较前次证据，不能把单段唯一性或只完成原文阶段当作全局唯一性。continue 在两个阶段中保留原检查 / 确认决定；完整检查点和进度可落盘重开，网络失败从上个已提交检查点继续。期间本机编辑 / 账号代次改变、强制中断 checking、选择仅本机或重新开始的处理沿用前述保护规则。

v8 只追加来源标记、operation 和 recovery_scan.segment_progress_json；segmented-v1 的 UIDNEXT 边界、当前段游标、滚动摘要和匹配信息存现有 checkpoint_json。进度显示已处理段 / 总段和已读候选，不能把尚在统计的候选数渲染成全局完成比例。每个任务仍仅推进一页或一个复核段。

每页开始和结束仍重查当前段完整 UID 集合，之后完成全段 validating；没有减少原文、来源或集合校验。检查点 JSON 序列化在 DB 锁外，格式探测不再额外创建完整 JSON Value 树。旧大区间检查点不在中途缩减范围，需要重新开始才能采用新密度估算。

账号验证与同步的 IMAP 输入已加入 socket 流式限额：单 literal 16 MiB、单命令响应 32 MiB、协议行 1 MiB / 10000 行、SEARCH token 合计 50000，单次上游读取最多 8192 字节。业务恢复仍保留声明大小 1 MiB / 单页 10 MiB 与实际长度校验；不因传输限额较大而放宽绑定。超限使连接永久失效，按网络失败保存上一完整检查点，不采用当前不完整页。详见 [IMAP_LIMITS](IMAP_LIMITS.md)。

恢复候选 SEARCH / 原文仍由 imap 库在更严业务限额内缓冲；正常收信的大原文已有分块落盘，不用于跳过恢复限制。UID 空洞很多时要检查多个空区间，频繁新信使 UIDNEXT 变化时会保守失效；没有跨目录事务快照。真实大邮箱、5 万封完整原文遍历的性能及服务端差异仍待验收。

Rust 回归入口 mail_recovery_tests.rs：旧缓存二次确认、UID / UIDVALIDITY / 内容 / 文件夹歧义、源 / 目标组合、候选和大小限额、断线 / 重开、核对期间编辑 / 账号改变 / 仅本机取消、回写派发竞争、未编辑副本合并 / 有编辑副本保留、SQL 回滚。原同步测试继续验证锁边界、稳定 ID 与游标。

TS 验证核对排在本机保存之后提交最新 revision、请求失败不宣称排队；Playwright 的 IPC harness 验证确认入口、明确重排、歧义提示、已登记请求恢复及连接失败重试。它们不等同于真实服务器或原生 WebView 成功验收。

新增 mail_recovery_scan_tests.rs 覆盖跨代新 UID、旧数值复用不误绑、后页重复、集合 / 代次改变、确认重扫、101 候选分页、断线续查 / 重开、期间编辑与锁边界、跨代未知归档两种恢复、硬上限和 v6 升级。浏览器验证进度、未完成无确认入口、失败续查、确认阶段继续扫描和后页歧义。

mail_recovery_extended_tests.rs 覆盖可信补齐的两步读取、无锚点 / 弱恢复不能升级、同正文但不同原文、期间编辑与 SQL 回滚、跨段确认重扫 / 重复、早期段删除后的全段摘要失效、UIDNEXT / 越界响应、密集 50000 UID 的单页请求、分段重开 / 断线续查、来源降级后旧确认不可绕过与 v7 升级。密集测试只读取一页原文，完整双阶段协议测试使用稀疏跨段样例；不称为真实五万封收信性能验收。

## A3.8：跨目录与自动续页

原 UID 被独立复核为 remoteMissing、且已有可信完整原文指纹时，可检查全部可访问目录（上限 128），不是只挑一个 Archive。源目录必须仍列出，不能猜重命名。保存每目录 UIDVALIDITY / UIDNEXT 固定边界、原始目录集合及顺序；源优先、其他排序，逐页 collecting + 全段 validating 与确认重扫不变。跨目录重复、目录集合变化、源不可访问或缺可信指纹均保留 unresolved / 原数据。

额外目录使用 folder-<原始名 SHA-256> 作用域，不能用显示名代替。明确恢复时再检查来源 / 版本；目标缓存按唯一当前代次精确 tuple 查找，多个目标拒绝；有编辑的目标仍不合并。退休旧缓存经 original_remote_id 显示原定位，确认成功才清除退休标记；普通同步不会自动赋给新账号邮件旧意图。

scanning 或带进度的失败可点击自动核对剩余页，登记 auto-continue；继续复用账号 worker，每任务一页 / 一个复核段。已授权续页在网络失败后退避续跑上个检查点，停止不自动重启。首次完整检查到 located 必停，只有明确确认后才能重新完整遍历并应用；保留本机 / 重新开始可取消证据。autoContinue 不能作为唯一性或授权恢复的证据。

完整原文缓存重取属于独立 imap_body 请求：要求可信当前定位、核对 UID / UIDVALIDITY / 内容 / generation / revision，恢复缓存与附件但不升级历史 content_hash_verified，也不改正文 / 本机意图。下载看到的相似内容不能补造历史指纹。

跨目录与自动续页测试在 mail_recovery_wide_tests.rs；它们验证两轮完整检查、后目录重复、新目录变化、弱来源拒绝、自动继续不越过明确确认及本地星标保留。真实服务端仍未验收。
